## 总体点评

在没有任何设计规范可依的前提下，这套视觉语言是自洽的：青=激活/主色、黄=未确认/假设、绿=正常/已确认、红=异常，各页面与遗留旧页共用同一套语义，跨页没有出现色义冲突。设备协同示意图是本轮完成度最高的部分——1120×470 固定舞台、中枢节点高亮、虚线流动动画、「评审建议/假设」角标齐备，既传达了结构又没有伪造实时数据，正合这个 PRD 对「不冒充现场还原」的要求。异常卡片的缺图态处理得体，缺失态与正常态在视觉上可区分而不刺眼。

主要风险集中在**观看距离**与**版面容量**两件事上。这是一个给客户领导在物理大屏前看的产品，但正文与说明文字大量使用 11–13px：`.cc-node p` 13px、`.cc-step-duty` 13px、`.cc-cap-label` 12.5px、`.cc-mo-card-meta` 11.5px，而标题 30px、数字 26px。层级断崖导致只有标题和数字能在墙距看清，所有解释性内容在实际观看条件下失效。运营驾驶舱页面高约 1959px，1440×900 溢出 1059px、1920×1080 仍溢出 879px，16:9 大屏只能显示上方约 40%。

值得保留的亮点：`.cc-mo-shot-missing` 把「图片暂不可用」做成明确的空态而非破图；底部导航已改为吸底，任何分辨率下都能点到；页面切换器作为评审专用件有独立的视觉身份。

## P0-P3 优先级问题

### P1 - 响应式在 ≤1024 全面失效

- 证据：`.cc-screen{min-height:100vh;min-width:1180px;...}`（`style.css`）。全文件仅 5 个 `@media`，其中只有 1 条作用于 `cc-` 页面（`@media(max-width:1250px)`），且只重排网格列数（`.cc-equip-grid` 5→3 列、`.cc-mo-grid` 4→2 列等），**没有任何 <768px 断点**。实测 1024×768：1180px 画布比视口宽 156px，右侧被硬裁——行为监控第 3 列统计卡被切、顶栏文字截断、设备卡整列被切，需横向滚动才能看到，且无溢出提示。实测 390×844：逐行采样显示最右列 83/121 行为非背景像素，即内容被切掉右侧 790px，而非重排；顶部元信息、右半图表与全部底部导航均在屏外。
- 影响：1024 是评审与投影的常用尺寸，内容被静默裁切会直接影响评审结论；该行为也违反 PRD:226-233「适配不同屏幕，不得简单拉伸导致图片变形或文字过小」。大屏原型放弃移动端可以接受，但 1024 档被静默裁切属实际可用性缺陷。
- 修复方向：若确定只支持大屏，把 `min-width` 改为显式声明并在规格中写明支持分辨率；否则改为 `width:100%;max-width:1180px`，并把 1250 断点下沉到 1024/768，为顶栏与统计卡增加换行策略。

### P1 - 正文与说明文字 11–13px，墙距不可读

- 证据：`.cc-node p` 13px、`.cc-step-duty` 13px、`.cc-equip-purpose` 13px、`.cc-cap-label` 12.5px、`.cc-mo-card-meta` 11.5px、`.cc-note-card p` 12.5px（均见 `style.css`）；对照标题 30px、二级标题 24px、统计数字 26px。
- 影响：大屏的核心使用场景是数米外观看。11–13px 在墙距下不可读，等于所有解释性文案（节点职责、环节说明、设备用途、能力标注、事件元信息）都无法传达，只剩下标题与数字——而这些解释性文字恰恰承载了本 PRD 最看重的「候选≠已部署」「能力待确认」等限定语义，读不到就等于约束没传达到。
- 修复方向：正文抬到 16–18px，次要信息不低于 14px；或改为 1920 画布基准 + 整体等比缩放，让字号随分辨率放大。

### P1 - 运营驾驶舱页面无法在 16:9 大屏完整呈现

- 证据：精确视口实测（`Emulation.setDeviceMetricsOverride`）该页 `scrollHeight` 为 1959px，`.cc-body` 高 1648px。1440×900 溢出 1059px；1920×1080 溢出 879px。对照行为监控页在 1920×1080 下 `overflow=0`（可完整呈现），在 1440×900 下溢出 131px。
- 影响：该页按可滚动长看板构建，而交付形态是固定横屏大屏。客户领导实际只能看到上方约 40%，「设备运行状态」以下内容在物理大屏上不可达。底部导航经吸底处理后已可点击，但内容容量问题不因此缓解。
- 修复方向：压缩为 16:9 单屏（合并或削减模块）、拆为两页、或明确接受滚动并把讲解改为 iPad 驱动分页。需业务方先确认必看指标，不宜由实现单方面裁剪。

### P2 - 两处文字对比度低于 WCAG AA

- 证据：按 WCAG 相对亮度公式逐对计算 63 组前景/背景，2 组不达标。`.cc-mo-stat em`：前景 `#7da8d1`、背景 `#10417f`、字号 11px，比值 **4.03:1**（算术：`L(#7da8d1)=0.36969`，`L(#10417f)=0.05423`，`(0.36969+0.05)/(0.05423+0.05)=4.027`），低于普通文本要求的 4.5:1；`.cc-mo-stat` 自身为不透明渐变，该失败与页面背景渐变无关，确定失败。`.cc-flow-arrow span`：前景 `#5f92bb`、背景 `#103d78`、11px，比值约 **3.22:1**，同样不达标；该处背景取自页面径向渐变中部，实际落点接近 `#103d78`，存在真实失败风险。其余 61 组均 ≥4.5:1。
- 影响：这两处都是 11px 小字，本身已接近可读性下限，叠加对比度不足后在墙距下基本无法辨认。
- 修复方向：`.cc-mo-stat em` 前景改为 `#a8c9e4` 或将字号提到 12px 以上；`.cc-flow-arrow span` 前景改为 `#83add3`（可达 ≥4.5:1）。

### P2 - 可访问性语义与焦点状态缺失

- 证据：`style.css` 中 `:focus` / `:focus-visible` / `outline` **0 命中**（全文件仅 2 处 `focus` 子串，均为遗留 `.dt-stage-focus` 类名），即没有任何作者定义的焦点样式。状态类选中态仅通过 `className="active"` 表达，周期按钮与数据状态按钮均缺 `aria-pressed`（`pages/DisplayControl.tsx`）。`components/PageSwitcher.tsx` 使用 `role="menu"`，但其子节点混入了 `.cc-switcher-head`、`.cc-switcher-split` 等非 `menuitem` 元素，且未实现方向键导航。
- 影响：深蓝主题下依赖浏览器默认焦点环，可见性不稳定；读屏用户无法得知当前选中的统计周期与数据状态；非法的 `menu` 结构会使屏幕阅读器的菜单模式失效。
- 修复方向：补充 3–4 条 `:focus-visible` 规则（可参照同仓其他原型的写法）；为周期与数据状态按钮加 `aria-pressed`；去掉 `role="menu"/"menuitem"`，改用普通按钮列表 + `aria-label`。

## 核心元件

### 顶栏（Header / Hero）

各展示页由 `DisplayShell` 统一：品牌标题 + 副标题 + 「客户／项目名称：待确认」占位 + 「当前页面 · {页名}」+「演示数据」角标，信息结构清晰，跨页一致。iPad 控制页另起 `cc-control-top`，结构合理但丢失了「演示数据」标识。调整点：占位符「待确认」常驻客户可见区，评审时应替换或仅在评审模式显示；「演示数据」角标 13px 与占位符同级，权重偏低，容易被 26px 的数字压过去。

### 底部导航（Navigation）

`DisplayNav` 的状态、禁用逻辑与激活态表达统一，短标签与页标题的轻微不一致（「烹饪流程」vs「无人烹饪流程」）可接受。本轮已改为 `position:sticky;bottom:0` 并补背景色，实测 1440×900 与 1920×1080 下两页导航均可见，且本来就能放下的页面零布局变化（1920×1080 行为监控页导航仍在 997–1060）。保留点：吸底方案在不改布局的前提下解决了可达性。

### 设备协同示意图

本轮完成度最高的元件。1120×470 固定舞台、中枢节点高亮与角色标注（中枢／加工节点／器具）层级分明，虚线区分「评审假设关系」而非伪装已确认关系，与 PRD 要求高度契合。调整点：固定 px 尺寸无缩放策略，在 1920/4K 上不会放大，观感会偏小；建议改为按容器等比缩放。

### 流程步骤

信息完整（环节名、参与设备、职责、输入→输出），人工环节与并行路径的徽标区分清楚。调整点：横向箭头内的文字被隐藏（`style.css` 中隐藏了 `.cc-flow-arrow span`），导致 01→02、05→06 的串行关系与并行栅格在视觉形态上过于接近，串/并行主要靠虚线框区分，语义偏弱。

### 设备卡片

结构统一，型号/数量「—」的缺省规则表达清晰。调整点：卡片普遍偏「未完成」——五张卡几乎全是黄色「待确认」，占位框为虚线，容器/层架卡留白明显，客户第一眼容易读成「什么都还没定」，同时稀释了黄色告警色的语义。

### 异常卡片

与遗留 `dt-` 卡片同构（青头 + 图 + 红标），信息层级清楚，8 张卡在 1920×1080 下排布稳定。缺图态 `cc-mo-shot-missing` 处理得体，是加分项。调整点：抓拍图高度 126px 偏小（遗留页同类图片为 190px），「看抓拍图」这一核心任务的效率受影响；异常标签 11px 在墙距吃力。

### iPad 控制页

必备信息齐全（目标大屏、连接状态、当前展示、页面按钮、返回首页、周期筛选、演示开关），断连与切换失败分支完整且不虚报成功，是本原型的可信度来源。调整点：页面在 1440×900 下超出首屏，演示开关与页脚需滚动才能看到，而演示开关恰是讲解异常分支时要用的控件，建议固定视口高度 + 内部滚动，或把演示开关折叠。

## 响应式与可访问性

- **桌面**：1440×900 与 1920×1080 下行为监控页正常（1920×1080 完整无溢出）；运营驾驶舱两档均严重溢出（见 P1）。
- **平板**：1024×768 下 `.cc-screen` 的 `min-width:1180px` 导致右侧 156px 被硬裁，网格列数虽已重排但画布宽度不受控（见 P1）。
- **移动端**：390×844 下内容为 1180px 画布被切掉右侧约 790px，并非重排，底部导航与顶栏元信息均在屏外。大屏原型不要求移动端支持，但当前 CSS 也没有任何降级声明。
- **键盘**：所有交互元素均为原生 `<button>`，共 24 个，无 `tabIndex=-1`，`disabled` 按钮正确移出 Tab 序，`outline:none` 无替代的情况 **0 处**，默认焦点环未被抑制。缺口在**没有作者定义的焦点样式**，深蓝主题下默认环可见性不稳定（见 P2）。
- **语义**：`div`/`span` 带 `onClick` **0 处**，无缺失 `role` 的点击元素；已有 `nav[aria-label]`、`aria-current="page"`、`aria-expanded`、装饰 SVG `aria-hidden`。缺口在状态暴露与 `role="menu"` 用法（见 P2）。
- **对比度**：63 组实测，2 组低于 4.5:1（见 P2），其余通过。

## 证据与评估说明

- **浏览器/截图**：使用。Chrome headless 通过 CDP（`Emulation.setDeviceMetricsOverride`）在精确 1440×900、1920×1080、1024×768、390×844 视口下截图与取数，未依赖 `--window-size` 近似值（该方式实测内视口为 757px，会得出错误结论）。溢出与导航可见性均为脚本实测数值，非目测。
- **Scanner**：未使用 `rules/references/impeccable/scripts/detect.mjs`，以避免 detector 输出先污染设计判断；改用直接读取 `style.css` 规则与浏览器实测。
- **独立评估**：`full`。按设计评估（目标、源码、截图）与证据评估（响应式、可访问性、实现风险）两个互不干扰的视角分别执行，各自完成前未暴露结论，由主代理核实后合并。
- **误报剔除记录**：子代理曾报「iPad 控制页 `.cc-control-frame{width:540px;max-width:100%}` 的 `max-width` 失效」并定为 P1，经复核该失效仅在 390px 手机宽度下出现，而该页是 iPad 控制页（目标 1024 起），1024/1440 下框宽 540px 正常居中，故严重度下调，未计入 P1 清单。
- **降级说明**：本原型无 `DESIGN.md`，因此「设计一致性」维度只能评估跨页自洽性，无法评估与设计规范的符合度。这是本次评审最主要的覆盖缺口，已在评分依据中计入。
