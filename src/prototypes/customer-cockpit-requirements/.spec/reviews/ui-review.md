## 总体点评

视觉系统本身是自洽的：青=主色／激活、黄=假设／待确认、绿=正常、红=异常，三页与保留的 `dt-` 生产驾驶舱共用同一套深蓝控制室语言，没有色义冲突；图表做了「图例 + 口径小字」，没有伪装成实时数据。**本轮最值得记录的成绩是运营驾驶舱的单屏改造**——精确视口实测 1440×900、1920×1080、2560×1440 溢出均为 0，此前「无法在 16:9 完整呈现」的问题已闭环。

但这次压缩是**用缩字号换高度**，代价直接压在可读性上：运营驾驶舱 1920×1080 下 123 个文本叶节点中有 54 个（44%）小于 12px，最小 **9.5px**，而这些小字恰好承载「演示」「待接入」「口径待确认」这些本 PRD 最看重的限定语义。同一页还有 3 处文字对比度低于 WCAG AA，其中烹饪区图上的黄底白字状态标只有 **1.85:1**，在强光或远距下几乎只剩色块。换言之：现在**放得下**了，但放下的是一屏读不出细节的图。

其余风险集中在**响应式的降级质量**：从声明的 `min-width:1180px` 起，投料区两个物料标签就被压到 `clientWidth = 0`（整段文字消失，不是省略号），顶栏 H1 与「客户／项目名称：待确认」标签重叠 15px；行为监控页在 1440×900 仍溢出 56px，与运营驾驶舱的「单屏」口径不一致；iPad 控制页在 iPad 横屏（1180×820／1024×768）需滚动才能触达演示开关。

## P0-P3 优先级问题

### P1 - 运营驾驶舱正文压到 9.5–11.5px，墙距可读性不成立

- 证据：`getComputedStyle` 实测（1920×1080）——`.cc-op-kpi em` **9.5px**、`.cc-op-material small` **9.5px**、`.cc-op-zone-card>small` / `.cc-op-zone-devices` / `.cc-op-chart-labels span` **10px**、`.cc-op-serving-columns span` / `.cc-op-label` **10.5px**、`.cc-op-station-row` / `.cc-op-chart-caption` / `.cc-op-material span` **11px**、`.cc-op-panel-head p` **11.5px**、`.cc-page-head p` / `.cc-op-progress-banner` **12.5px**、`.cc-op-progress-table td/th` **13px**。全页统计：`.cc-body` 内 123 个文本叶节点中 54 个 < 12px（44%），最小 9.5px。源码线索：`style.css:296-362` 整段 `.cc-cockpit-screen` 覆盖块（2026-09-29 单屏压缩时整体下调一档）。同壳层对照：行为监控页 KPI 数值 26px、正文 12–14px，即运营页被系统性下调约 20–30%。
- 影响：大屏的核心场景是数米外观看。9.5–13px 在墙距下不可读，等于所有限定语义（「演示数据」「待数据接入」「口径待确认」）与明细（出餐份数、投料状态、轴刻度）都无法传达，而这些恰是 PRD 最强调的「候选≠已部署」约束。压缩达成了单屏，但把信息密度换成了不可读。
- 修复方向：**用削减模块而非缩字号来回收高度**——例如把「计划与出成对比」柱状图与「用料与出成」四张卡合并（二者都在讲投料／出成，信息重叠），或把生产进度表从 8 行压到 6 行（`OperationsDashboard.tsx:20-29`）。同时给该作用域设字号下限（正文 ≥14px、次要 ≥12px）。若必须保留全部内容，则接受拆页，而不是继续缩字。

### P1 - 三处文字对比度低于 WCAG AA，且都在默认首页

- 证据（前景／有效背景／比值均为计算样式实测，主代理已独立复核）：
  - `.cc-op-zone-image span`（烹饪区图上的「烤箱 · 运行中」「炒菜机 · 运行中」）：`#ffffff` 11px/700 on `#f3b400` 实底 = **1.85:1**（要求 4.5）。来源 `style.css:249`（`background:#f3b400;color:#fff`），cockpit 作用域 `style.css:339` 把字号提到 11px。**硬失败**。
  - `.cc-cockpit-top-nav button.active`（当前页签）：`#ffffff` 20px/400 on 渐变 `#10b9da → #0d83bc` = **2.34:1（亮端）～4.21:1（暗端）**。20px 非粗体不满足「大文本」3:1 豁免。来源 `style.css:275`。
  - `.cc-op-progress-banner .unfinished`（「● 未完成 2」）：`#ff4870` 12.5px/700 on `#0f3d75` = **3.30:1**。来源 `style.css:261`。
  - 边际项（仅最亮色标不足、实际落点达标，未计入硬失败）：`.cc-op-kpi em`、`.cc-op-panel-head p`、`.cc-op-chart-labels span`、`.cc-op-zone-card>small`、`.cc-op-material small`、`.cc-op-foot`（`#7da8d1`/`#73a9d4` 对渐变最亮端约 4.03–4.27:1）。
- 影响：三处分别承载「设备运行状态」「当前所在页」「未完成任务数」三类关键信息，在目标大屏的观看条件下基本读不出，属 WCAG 2.x AA 失败。
- 修复方向：`.cc-op-zone-image span` 底色压深（如 `#a8760a`）或文字改深色 `#3a2a00`；`.cc-cockpit-top-nav button.active` 渐变压深至 ≤`#0a6d8c` 或改深色文字；`.cc-op-progress-banner .unfinished` 改用同页已验证达标的 `#ff8fa5`（`.cc-mo-banner` 用色，实测 5.0:1）。

### P1 - ≤1250px 出现文字完全不可见与顶栏重叠（不是重排，是消失）

- 证据（精确视口实测，主代理已独立复核）：
  - `.cc-op-station-row em`（投料区「切块土豆」「等待下一批次」）在 1180×820 与 1024×768 下 `clientWidth = 0`，而 `scrollWidth` 为 44 / 66 → **整段文字宽度归零、完全不可见**（不是省略号截断）。根因 `style.css:249` 的 `grid-template-columns:auto auto 1fr` 加上 `style.css:330` 把首列压到约 93px。即使在 1440×900，第二个标签也已 `clientWidth 48 < scrollWidth 66` 被截断。
  - `.cc-brand h1` 与 `.cc-project` 的包围盒重叠 **15px**，从 `style.css:26` 声明的 `min-width:1180px` 这个下界起就发生（`style.css:266` 品牌居中 + `:268` 元信息绝对定位）。
  - 1024×768 横向裁切 **156px**、纵向溢出 **510px**；390×844 横向裁切 **790px**。`.cc-screen` 宽度恒为 1180px，窄屏是硬裁不是重排；全文件作用于 `cc-` 页面的断点只有 `1250` 一个，无 <768 主断点。
- 影响：在**声明支持范围的下界**（1180px）就已出现文字重叠与标签消失；1024×768 是评审与投影的常用尺寸，被静默裁切且滚动条被预览壳隐藏，评审者可能误判为渲染故障。
- 修复方向：若确定只支持大屏，把支持分辨率写进规格并提高 `min-width`；否则顶栏改为 `flex-wrap` 或去掉 `.cc-top-meta` 的绝对定位，`.cc-op-station-row` 在窄宽度下改为两行布局（`grid-template-columns:auto auto` + `em` 换行）。

### P2 - 行为监控页在 ≤1600×900 溢出，与运营驾驶舱的「单屏」口径不一致

- 证据：CDP 精确视口实测，`behavior` 页 `docScrollHeight` 恒为 956px（宽度 ≥1250 时与宽度无关）：1920×1080 → 0；1600×900 → **56**；1440×900 → **56**；1366×768 → **188**。同一批视口下运营驾驶舱为 0／0／0。超出的内容为最后一排抓拍卡与页脚。
- 影响：两个兄弟展示页对「单屏」的达成度不同。非触摸、非滚动的大屏上，讲解到行为监控页会出现半截内容不可达，与运营驾驶舱刚达成的口径互相矛盾。
- 修复方向：把行为页纳入同一套单屏约束（`.cc-mo-shot` 现为 126px，可压缩；或 8 张卡在 ≤1600×900 时改为 3 列），或在规格中明确声明「支持分辨率 1920×1080 及以上」，避免用 1600×900／1366×768 交付。

### P2 - iPad 控制页在 iPad 横屏放不下，且 540px 固定框的 `max-width:100%` 失效

- 证据：`.cc-control-frame` 在所有视口恒为 **540×884**（`style.css:182`）。1180×820（iPad Air 11″ 量级）纵向溢出 **104px**；1024×768（iPad 横屏）溢出 **156px**；1440×900 溢出 24px。页脚两个「打开大屏」按钮与部分演示开关区在 iPad 横屏下需滚动才能到达，而演示开关正是讲解失败分支时要用的控件。390×844 下框架仍为 540px，横向溢出 170px——`style.css:182` 的 `max-width:100%` 因 `style.css:181` 的 `display:grid;place-items:center` 生成隐式 `auto` 轨道（按条目 max-content 540px 定宽）而失效。
- 影响：iPad 横屏是讲解人的主场景，主场景下无法一屏完成「切页 + 返回首页」的动作；同时 540px 窄框在 1180px 宽的横屏上左右各空约 320px，控件尺寸没有随屏幕放大。
- 修复方向：`style.css:181` 改为 `grid-template-columns:minmax(0,1fr)`（或把 `place-items:center` 换成 `justify-content:center`）让 `max-width:100%` 生效；横屏时改两列布局并把 `max-width` 放到 900–1000px；或固定 `height:100vh` + 内部区域滚动，保证演示开关与页脚常驻首屏。1024×768 应作为最低验收断点。

## 核心元件

### Hero / 页头（`DisplayShell` + `CockpitTopNav`）
信息结构清晰：品牌 + 副标题 +「客户／项目名称：待确认」占位 +「当前页面 · {页名}」+「演示数据」角标。**保留**：占位符与演示角标把「未确认」讲清楚，符合本 PRD 的诚实口径。**调整**：(a) 同一 `DisplayShell` 在两个大屏页渲染出两套页头——`operations` 走 `.cc-cockpit-screen` 变体（`style.css:266` 隐藏 logo 圆、品牌居中、导航按钮 58px、激活态用渐变），`behavior` 走基础 `.cc-*`（logo 可见、品牌左对齐、导航按钮 62px、激活态用纯色 `#13a4cc`）；同一产品两个兄弟页在客户讲解时切换会有明显「跳版」感，建议收敛为一种，仅在 `.cc-cockpit-screen` 保留背景网格这类皮肤级差异；(b)「客户／项目名称：待确认」常驻客户可见区，正式演示前应替换或仅在评审模式显示。

### KPI 卡（`.cc-op-kpi` / `.cc-mo-stat`）
两张卡同构但不同尺：运营页 21px／12px／**9.5px**，行为页 26px／14px／11px，行为页另把「全部异常」卡做成青色描边区分总量。**保留**：总量卡单独高亮是对的。**调整**：两页字号应对齐，而不是让「被压缩的那页」整体矮一档；运营页数值 21px 在墙距偏小，备注 9.5px 实际读不到。

### 运营驾驶舱：表格与图表
生产进度表结构标准但表体 13px 偏小；生产完成趋势折线有渐变填充、网格、数据点与 `role="img"` 语义，完成度高（但数据点与折线不重合，属业务数据问题，见原型评审 P1）；计划与出成对比柱状图用 `height:{value}%` 驱动，语义直白。**保留**：三张图都做了「图例 + 口径小字」，没有伪造成实时数据。**调整**：轴标签 10px、说明 11.5px 低于可读线；柱状图与下方「用料与出成」四卡信息重叠，是压缩高度的首选合并点。

### 生产状态区域卡（投料区／烹饪区／出餐区）
三段串联（投料→烹饪→出餐）与 PRD 口径一致，烹饪区嵌现场图 + 设备运行标注，层级合理，横向串联一眼能读懂流程。**保留**：结构清晰。**调整**：烹饪区图上的黄色状态标 1.85:1 对比度硬失败；出餐明细 10.5px、投料备注 10px 读不到；投料区物料标签在窄宽度下宽度归零。

### 行为监控抓拍卡（`.cc-mo-card`）
青头（类型 + 相对／绝对时间）+ 抓拍图（CAM 标签 + 红标类型）+ 元信息（区域 + 事件 ID），8 张在 1920×1080 稳定排布。**保留**：相对时间由 `monitorDemo.ts:122-131` 的 `formatRelative` 从时间戳算出，不是写死；缺图态 `.cc-mo-shot-missing` 用斜纹底 +「图片暂不可用」+ 保留事件其他信息，处理得体。**调整**：抓拍图仅 126px 高，「看抓拍图」这一核心动作的效率受限（保留页同类图为 190px），若仍要保 8 卡可考虑减到 6 卡放大图；页脚「含 1 条缺图事件」的声明与数据不符（见原型评审 P2）。

### iPad 控制页
连接状态、当前展示、切换失败保留原页 + 重试、按钮禁用逻辑完整，是全原型最可信的元件。**调整**：横屏两列化、把演示开关提到首屏内、`max-width` 放大（见 P2）。

### 导航
当前大屏页的底部导航已被关闭（`OperationsDashboard.tsx:54`、`BehaviorMonitor.tsx:76` 均 `showBottomNav={false}`），`DisplayNav` 与 `.cc-nav*` 实际不渲染；在架导航只剩顶部 2 按钮与右侧竖排 `PageSwitcher`。**保留**：顶部 2 按钮与 `DISPLAY_PAGES` 数量一致，无误导。**调整**：(a) 若确定不再需要底部导航，应删除 `DisplayNav` 与 `.cc-nav*`，避免留下「看起来可用实际不生效」的代码；(b) 右侧竖排「原型页面」在 1024／390 下压在 KPI 与生产状态区之上（`position:fixed;right:0;z-index:99`），虽标注「仅评审用」，仍会遮挡阅读，建议加收起态或移出内容区。

|---|---|---|---|---|---|---|---|---|
| operations | 0 | 0 | 0 | +131 | +458 | +510（横裁 156） | +153（横裁 790） | 0 |
| behavior | 0 | +56 | +56 | +188 | +703 | +755（横裁 156） | +679（横裁 790） | — |

- **桌面**：1920×1080 三页均完整；运营驾驶舱在 1600×900 与 1440×900 亦完整（本轮单屏改造的成果）。
- **平板**：1024×768 下 `.cc-screen{min-width:1180px}` 导致右侧 156px 被硬裁，且窄屏不是重排；iPad 控制页 1024×768 溢出 156px。
- **移动端**：390×844 下内容为 1180px 画布被切掉约 790px，底部导航与顶栏元信息在屏外。大屏原型不要求移动端支持，但当前 CSS 没有任何降级声明；`style.css:248`/`249` 两条 `@media(max-width:760px)` 的 `grid-template-columns` 已被 `style.css:316`/`330`（特异性更高）覆盖而**实际失效**（实测 390 下仍为 2 列／3 列）。
