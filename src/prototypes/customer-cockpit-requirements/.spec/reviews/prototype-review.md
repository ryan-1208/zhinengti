## 总体点评

原型在**状态、异常与恢复路径**上的完成度明显高于同类交付：行为监控五态（加载中／无事件／获取失败／监控未接入／正常）在源码与运行时都能逐一对上，切换失败保留原页并给重试、断连不虚报成功、缺失值不填零、相对时间由时间戳计算，这些是本原型可信度的真正来源。

本轮最严重的问题出在**默认首页的数据口径**：运营驾驶舱同屏三组数字互相矛盾——顶部条写「今日生产总数 12／已完成 2／未完成 2」，下方表格只有 8 行且仅 1 条「已出餐」；「出成率 92%」与柱状图「出成 61%」冲突；趋势图的折线与数据点由两套硬编码坐标生成，圆点根本不在线上。该页是客户领导打开大屏看到的第一屏，直接冲击 PRD 最强调的「不伪造数据」立场。同时，主规格仍未承接 PRD 的非功能要求章节与三条关键业务规则（未授权禁用切页、称重能力≠称重数据可读、不显示虚构进度），「未授权」在规格与实现中都没有落点。

值得保留的有效表达：以「演示数据／待接入／待确认」贯穿三页的显式标注体系；行为监控把「缺失不等于零」做成独立状态而非空值；iPad 控制页的断连与切换失败分支完整且不虚报成功。本轮另已闭环上一版的 P1「运营驾驶舱无法在 16:9 大屏完整呈现」——精确视口实测 1440×900、1920×1080、2560×1440 溢出均为 0。

## P0-P3 优先级问题

### P1 - 运营驾驶舱（默认首页）数据口径不自洽

- 证据（源码确定性，主代理已逐条复核）：
  - 顶部条与表格/看板互相矛盾：`pages/OperationsDashboard.tsx:81` 写「今日生产总数 12／● 已完成 2／● 未完成 2」，而 `:20-29` 的 `PROGRESS_ROWS` 只有 8 行、按状态为已出餐 1／预处理完成 4／待生产 3；`:11-18` 的 KPI 又是计划 1,200／已完成 768。2+2=4≠12，且「已完成 2」与表格中唯一一条「已出餐」对不上。
  - 出成口径冲突：`:35` 卡片「出成率 92%」与 `:40-44`（渲染于 `:105`）柱状图「出成 61%」矛盾；按 计划 82／投料 68 计算，出成率应为 61/82≈74%，且偏差应为 −17%，而 `:34` 写「+0.8%」。
  - 图表自相矛盾：`:94-95` 折线与填充用硬编码坐标 `18,127 106,112 194,118 282,88 370,82 458,54 548,36`，`:96` 的圆点由 `135 - PRODUCTION_TREND` 生成（cy = 93/80/86/67/63/51/43），同一条「完成任务数」序列的点与线不重合。
- 影响：默认首页是客户领导的第一屏，三组互相矛盾的数字会被现场直接质疑，削弱「不伪造数据」这一核心可信度；验收时也无法确定应以哪一组为准。PRD:211 明确「不显示虚构的任务百分比」，本页的数据关系属于虚构范畴。
- 修复方向：让同一口径只由一个数据源派生——进度条与表格共用一份任务数组（可参考 `index.tsx:102-108` 用 `filter` 派生 summary 的写法），用料卡与柱状图共用一组数值，折线 `points` 与圆点 `cy` 由同一数组生成；「今日生产总数」与「已完成／未完成」的计数关系需业务方给出定义后再落地。

### P1 - 主规格未承接 PRD 的非功能要求与三条关键业务规则（上一版遗留，未闭环）

- 证据：
  - 非功能要求整章未承接：`src/resources/prd/客户驾驶舱需求PRD.md:248-255` 有六组要求（适配／可读性／稳定性／兼容性／网络／数据与素材），而 `.spec/spec.html` 中「非功能」「稳定性」「拉伸」「白屏」关键词命中数均为 0。例如 `PRD:251`「不得简单拉伸导致图片变形或文字过小」、`PRD:252`「持续展示期间切页不白屏」在规格中无对应条款。
  - 「未授权」无落点：`PRD:143` 要求「未授权或目标大屏未连接时，禁用切页并说明原因」。未连接分支已实现（`pages/DisplayControl.tsx:43`、`:129`、`:153`），但未授权分支在 `components/displaySync.ts:120-127`（仅有 connected 布尔）与整个控制页中均不存在，规格中「未授权」命中数为 0，`spec.html` 只把授权方式列为待确认。
  - 称重「能力」与「数据可读」未区分：`PRD:199`/`PRD:217` 要求两者不可互相推导，规格仅把称重整体归入「待接入」。
  - 不显示虚构进度未成文：`PRD:211` 的规则在规格中无对应条目（而 P1-1 正是该规则被违反的实例）。
- 影响：AC10（屏幕适配、无裁切）与 AC11（设备能力不夸大）在规格层没有验收依据；权限边界不完整；后续实现存在把「设备具有称重能力」推导为「系统可读取称重数据」的风险。
- 修复方向：在规格新增「非功能要求」章节逐条承接 `PRD:248-255`；把「未授权禁用切页」「称重能力≠称重数据可读」「不显示虚构进度」补入对应页面模块与「验收关注点」。部分规则可能已在实现中体现，但规格作为事实依据必须先落文档。

### P2 - 行为监控「含 1 条缺图事件」的声明与数据、规格均不符

- 证据：`pages/BehaviorMonitor.tsx:170` 页脚硬编码「含 1 条缺图事件，用于演示缺失态」；但 `components/monitorDemo.ts:54-85` 三个周期的全部事件都带 `image`，无任何缺图记录；`spec.html:451` 也明确「8 条事件均展示抓拍示例图，不设置缺图演示记录」。结果 `BehaviorMonitor.tsx:32` 的「该事件未返回抓拍图」文案在数据层不可达。
- 影响：页面断言了一个演示中不存在的状态；`PRD:267` 的 AC07 明确要求「缺图、空数据和加载失败时页面仍可用」，该分支目前只能靠图片加载失败偶然触发，无法在交付物上稳定验收。
- 修复方向：二选一——补一条 `image` 缺省的事件并同步 `spec.html:451`，或删除页脚该句声明。若保留该能力，建议再加一个可强制缺图的深链或演示开关。

### P2 - 演示数据存在重复事件编号

- 证据：`components/monitorDemo.ts:67`（week 周期，`EV230922004`，加工台 02）与 `:76`（month 周期，`EV230922004`，加工台 01）编号相同、时刻相同、区域不同；核验 24 个 id 仅 23 个唯一。该编号同时是抓拍卡的 React key（`BehaviorMonitor.tsx:145`）。
- 影响：同一编号对应两条字段冲突的事件，容易被读成同一事件被渲染两次；React key 重复会掩盖列表 diff 问题，接真实数据后会掩盖去重缺陷。上一版已标记，本轮仍未闭环。
- 修复方向：把其中一条改为未占用编号，并核对同号事件的时间／区域一致性。

### P2 - 不可达代码与死样式未清理

- 证据：`index.tsx:86-88` 的 `FrontCockpit` 首行即 `return <SafetyCockpit />`，其后整段 JSX 永不执行；`index.tsx:182-187` 的 `buildAlarmHtml` 全仓无调用；`index.tsx:147` 的 `NutritionCockpit` 不可达（唯一能改 group 的按钮只有 `production`/`behavior`，`nutrition`/`safety` 取不到）；`components/DisplayNav.tsx` 在架两页均以 `showBottomNav={false}` 关闭，实际不渲染，其 `.cc-nav*` 样式同步失效；`style.css:136-145`、`:248` 中 `.cc-op-task*`／`.cc-op-device*`／`.cc-op-energy*`／`.cc-op-alert*`／`.cc-op-image-frame` 等在当前 DOM 中无对应元素；`style.css:246` 的 `.cc-op-lower-grid` 断点被 `:257` 同特异性、位置更后的规则永久覆盖。
- 影响：评审据代码判断范围会误判（例如以为存在明厨亮灶／客诉子页），维护噪声增加；被覆盖的规则会让后续按「已有断点」判断响应式覆盖度时出错。
- 修复方向：删除或集中注释并标注「已下线，保留可恢复」；对确实失效的断点规则提升特异性或删除。
