# 排产餐段状态模型设计

> 版本：V0.1（草案，待评审）
> 范围：在现有倒排排程逻辑之上，定义「餐段状态」的判定规则、流转关系与展示口径。
> 不改动排程算法本身。

---

## 1. 设计目标

把口头的业务规则（"已过餐段只有及时出餐和延迟出餐，未完成只出现在当前餐段和即将到来的餐段"）转化为**可实现的判定函数**，并统一展示口径。

三条硬约束：

1. 已过餐段的终态只有「及时出餐」或「延迟出餐」，不得出现「未完成」。
2. 「未完成」只可能出现在当前餐段和即将到来的餐段。
3. 量的保证优先于时间——宁可多做不可少做，宁可延迟不可少做。

---

## 2. 领域对象与字段

| 对象 | 字段 | 说明 |
|------|------|------|
| 餐段 MealPeriod | `id`、`name` | 早餐 / 午餐 / 晚餐 / 夜宵 |
| | `start` | 餐段开始时刻 |
| | `deadline` | 出餐截止时刻（排程的 `T`） |
| | `end` | 餐段结束时刻 |
| | `planned` | 是否已生成排程 |
| 排程结果 Schedule | `prep_start` | 预处理开始（倒排链条末端） |
| | `weigh_start` | 称重开始 |
| | `cook_start` / `cook_end` | 烹饪起止 |
| | `serve_at` | 出餐时刻（计划值为预计，实际为回填） |
| 状态 PeriodStatus | `state` | `PLANNED` / `PENDING` / `ON_TIME` / `DELAYED` |
| | `delay_seconds` | 延迟时长 |

**份量口径（保量机制）**：盆数 `N = ceil(Q / M) × k`，层数 `ceil(N / C)`。
向上取整是**有意为之的保量保证**，不是精度缺陷——投入量恒 ≥ 需求份数。

---

## 3. 状态定义

| 状态 | 标识 | 含义 |
|------|------|------|
| 计划中 | `PLANNED` | 尚未生成排程，不参与状态判定 |
| 未完成 | `PENDING` | 已排程、尚未出餐，且**截止时刻未到** |
| 及时出餐 | `ON_TIME` | 出餐时刻 ≤ 截止时刻 |
| 延迟出餐 | `DELAYED` | 出餐时刻 > 截止时刻，或已过截止仍未出餐 |

**关键点：「未完成」的语义是"还有机会准时"。** 截止时刻一过，机会窗口关闭，状态立即转为延迟——而不是等到实际出餐才判定。

---

## 4. 判定函数

```
judge(period, now, serve_at):

    # 1. 已有出餐时刻 —— 直接与截止时刻比较，终态
    if serve_at is not None:
        if serve_at <= period.deadline:
            return ON_TIME,  delay = 0
        else:
            return DELAYED,  delay = serve_at - period.deadline

    # 2. 尚无出餐时刻
    if not period.planned:
        return PLANNED, delay = 0

    if now <= period.deadline:
        return PENDING, delay = 0          # 还有机会准时

    # 3. 已过截止、仍未出餐 —— 在途延迟，延迟时长持续累计
    return DELAYED, delay = now - period.deadline
```

**这个函数自动满足约束 1。** 已过餐段意味着 `now > period.end > period.deadline`，走不到 `PENDING` 分支，因此「未完成」在数学上不可能出现于已过餐段——不需要额外的兜底判断。

**约束 2 由 `planned` 标志承担。** 只有已生成排程的餐段才进入判定；更远的餐段处于 `PLANNED`，既不显示「未完成」，也不计入任何完成率。

### 延迟时长的两种形态

- **在途延迟**：`delay = now − deadline`，随时间增长，尚未定格。
- **定格延迟**：`delay = serve_at − deadline`，出餐后不再变化。

展示时应区分：在途用「已延迟 +17 分（仍在累计）」，定格用「延迟 +17 分」。

---

## 5. 状态流转

```
                    排程生成
   PLANNED ──────────────────────▶ PENDING
                                     │
              ┌──────────────────────┼──────────────────────┐
              │                      │                      │
      出餐 ≤ 截止             now > 截止，未出餐        出餐 > 截止
              │                      │                      │
              ▼                      ▼                      │
          ON_TIME                DELAYED（在途）             │
                                     │                      │
                                 实际出餐                    │
                                     ▼                      ▼
                                DELAYED（定格）◀────────────┘
```

流转规则：

- 终态 `ON_TIME` / `DELAYED` **不可回退**。
- `PENDING → DELAYED` 是**时间驱动**的自动流转（跨过截止时刻即触发），不依赖任何人工操作。
- 已过餐段的状态必然落在终态上；若出现 `PENDING`，即为状态结转故障，需告警。

## 6. 展示口径

### 6.1 指标口径修正

| 旧口径 | 问题 | 新口径 |
|--------|------|--------|
| 完成率 = 已完成 / 总数 | 保量机制下恒为 100%，无区分度 | **及时率** = 及时出餐餐段数 / 已结清餐段数 |
| 未完成数 | 未限定时间窗，会把远期餐段算进来 | 仅统计**当前餐段 + 即将到来的餐段** |
| — | — | **平均延迟时长**（仅对 `DELAYED` 餐段计算） |

### 6.2 视觉与文案

| 状态 | 填充 | 文字 | 文案模板 |
|------|------|------|----------|
| 计划中 | `#F1EFE8` | `#5F5E5A` | 待排程 |
| 未完成 | `#E6F1FB` | `#185FA5` | 剩余 2 小时 15 分 |
| 及时出餐 | `#EAF3DE` | `#3B6D11` | 06:28（提前 2 分） |
| 延迟出餐 | `#FAEEDA` | `#854F0B` | 11:47（延迟 17 分） |

延迟时长超过阈值（建议 30 分）时升级为红色 `#FCEBEB` / `#A32D2D`，并加注原因标签。

## 7. 三个边界问题的建议默认值

| # | 问题 | 建议默认 | 理由 |
|---|------|----------|------|
| 1 | 已过餐段但生产仍在进行 | 记为**延迟出餐（在途）** | 截止已过，结果已确定；继续挂「未完成」会掩盖问题 |
| 2 | 「未完成」的边界 | 取**截止时刻**，非餐段结束 | 截止一过即失去准时可能，早暴露优于晚暴露 |
| 3 | 更远的餐段显示什么 | 显示**待排程**（`PLANNED`） | 未排程即无完成/未完成可言，且不入任何完成率分母 |

> 若业务上更希望"餐段结束才结转"，只需把 §4 的 `now <= period.deadline` 改为 `now <= period.end`，其余结构不变。这是一个单点开关。

---

## 8. 与现有排程逻辑的接口

- 本模型是**派生层**，不侵入 `greedy_scheduler` 及其三个入口（`single_schedule`、`single_schedule/v2`、`multi_canteen_schedule`）。
- 所需输入仅三项：`period.deadline`、`period.planned`、`serve_at`。
- 倒排链条给出的 `serve_at` 为**预计值**；实际出餐回填后覆盖，状态随之从在途转为定格。
- 由于倒排不做可行性校验、永不报错，`serve_at` 在排程成功时必定存在，因此不存在"排不出来"的中间态——来不及的唯一表现就是 `serve_at > deadline`，即延迟出餐。
