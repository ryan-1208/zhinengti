## 修复：智厨生产流程「托盘没进设备就出餐」

- 文件：`src/prototypes/customer-cockpit-requirements-2/index.tsx`（`ACTIVE_ROUTE_PATHS`）
- 现象：流程演示动画里有的菜（番茄炒蛋）不在烹饪设备停留，直接飞向出口。
- **根因（几何核验得出）**：`animateMotion` 的 `keyPoints` 必须等于「目标设备中心在该路径上的弧长比例」。番茄炒蛋路线写的是 `0.2962`，实际反算该比例对应坐标是 `(350,240)` —— 即投料区出来的**岔路口**，不是炒菜机 CCJ2（中心 566,162）。所以托盘在路口停 2.5 秒后直接去出口。
- **正确值（用贝塞尔采样 + 累积弧长反算，可复现）**：CCJ1=0.4595（(458,162)）、CCJ2=**0.6023**（(566,162)）、KX1=0.5260（(510,318)）。原 CCJ1/KX1 两条本来就对，只 CCJ2 错。
- 修复：`keyPoints: '0;0.6023;0.6023;1'`；同时把 `pauseStart/pauseEnd` 与 `keyTimes` 从 `0.2429/0.4229` 调整为 `0.32/0.5`（停留仍为 14s×18% = 2.5s，与另两条一致；三条错峰落在 0.32/0.3768/0.4313）。
- 已加注释固化约束：keyPoints 中间值 = 设备中心在路径上的弧长比例；pauseStart/pauseEnd 必须与 keyTimes 中间两帧一致（否则设备高亮与托盘位置对不上）。
- 核验脚本思路：解析 `path` 的 M/C 指令 → 每段三次贝塞尔采样 400 点 → 累积弧长 → 按比例取点，与设备 `rect` 范围比对。

## 重做：智厨生产流程三条托盘的起点与节奏（"先进入入口，再出现"）

- 文件：`src/prototypes/customer-cockpit-requirements-2/index.tsx`（`ACTIVE_ROUTE_PATHS` 全量重写 + `dishState` 阈值）
- 用户原话：「番茄炒蛋为什么绕了一圈」→ 否掉我给的 3 个方案（竖直下降 / 拉直 / 保持）→「应该按逻辑来啊 **先进入入口 再出现** 而不是直接出现」。
- 定性：问题不在"绕"，在于**唯一一条从通道中段 x=276 起步的路线**（另两条从 x=134 起步），托盘凭空出现在通道右侧还往回折一段。用户的准则是通用规则，所以三条一起改。
- **新规则（已写进代码注释固化）**：
  1. 三条路线统一从**投料区入口通道左边缘 x=74** 驶入（一个入口、一条动线，符合"先进入入口再出现"）；
  2. 路径全程**单向**（`minx=起点x`，采样到的 x 单调不减，只在循环回绕时归 74）；
  3. `keyTimes` 中间两帧 = **弧长比 × (14-2.5)/14** 与再 **+2.5/14** —— 保证匀速行驶 + 停留恒为 2.5 秒。旧代码只改 keyPoints 没同步 keyTimes，导致番茄炒蛋前半段"飞速"（0.6023 弧长挤在 0.32 时间内）；
  4. `delay` 让三段停留均匀错开在 0s / 4.67s / 9.33s（实际值 -1.05s / -7.21s / -11.09s），任意时刻只有一台设备在烹饪；
  5. `trayStart/trayEnd` = 托盘位于**入口 2 通道（viewBox x 214~336）**的时间区间，由弧长区间换算（≈0.140~/0.265），入口 2 的等待卡片按它点亮。
- **新三条路径**：
  - 青椒肉丝 `M74 190 C150 190 260 232 350 240 …` len 839.3，CCJ1 弧长比 0.4972，keyTimes `0;0.4084;0.587;1`
  - 番茄炒蛋 `M74 240 C160 240 265 240 350 240 C450 240 516 185 566 162 …` len 810.9，CCJ2 弧长比 0.6273，keyTimes `0;0.5152;0.6938;1`
  - 蒜蓉娃娃菜 `M74 300 C160 320 262 265 350 240 C400 240 450 280 510 318 …` len 834.8，KX1 弧长比 0.5585，keyTimes `0;0.4588;0.6374;1`
  - 三条长度差 <3.5%，速度 ≈70~73 单位/秒。
- `dishState()` 里写死的 `phase < 0.25` 改成 `phase < route.trayEnd`，让状态词与托盘位置说的是同一件事。
- **验证方法（可复现，比截图可靠）**：CDP 采样，把 token 的 `getScreenCTM()` 结果用 `svg.getScreenCTM().inverse()` 反算回 viewBox 坐标（**直接读 `getCTM()` 会拿到"用户坐标→渲染像素"的矩阵，被 viewBox 缩放系数污染，数值全错**）。
  - 结果：三条停留点分别 (458,162)/(566,162)/(510,318) —— 与设备中心**完全相等**；x 单调不减，唯一"回退"是 14 秒循环回绕；番茄炒蛋轨迹 97→214(入口2左界)→336(入口2右界)→567→850，opacity 在 x=97~172 之间由 0.29 升到 1.00（即"边驶入边显现"）。
  - 入口 2 等待卡片：卡片亮起时对应托盘 x 恰好在 220~320 区间内，离开通道即熄灭，三条都同步。

### 收窄到「单餐段」后暴露的 3 个演示数据一致性问题（已量证，待用户定夺）
按 500ms 采样 16 个周期 × 3 个餐段（脚本 `/tmp/feedkpi.py`），得到：

| 餐段 | 行数 | 投料区 KPI 取值 | 状态组合数 | 状态实测 |
|---|---|---|---|---|
| 早餐（UTC 08:07） | 3 | {0, 1} | 12 | 取餐完成 / 未开始 / 取餐完成 |
| 午餐（Moscow 11:07） | 4 | {0, 1} | 22 | 摆盆中 / 烹饪完成 / 烹饪中 / 烹饪中 |
| 晚餐（Shanghai 16:07） | 3 | **{0}（恒为 0）** | **1** | 烹饪中 / 烹饪中 / 烹饪中 |

1. **晚餐「投料区」恒为 0**：演示动线 `ACTIVE_ROUTE_PATHS` 只有 3 条 —— 蒸蛋羹（早餐）、青椒肉丝 + 番茄炒蛋（午餐）。晚餐三道菜没有动线 → 按餐段过滤后必然 0。午餐两条动线的 tray 窗口（各 ~1.7s）错开 6.16s 从不重叠，所以最多也只到 1，到不了 2。
2. **晚餐状态列全是「烹饪中」**：无动线的菜走兜底 `done === total ? 取餐完成 : done > 0 ? 烹饪中 : 未开始`，晚餐三道是 2/3、2/3、1/3 → 三个都命中 `烹饪中`，一列看下来像写死了。
3. **动线菜的「状态」与「盆数」会打架**：状态取自动画相位（14s 一循环，会回到 `未开始`），盆数取自静态 demo 数据。早餐 `蒸蛋羹` 就出现 **状态=未开始 但 盆数 2/3 盆**，而顶部 KPI「已完成 7 盆」里已经把它那 2 盆算进去了。根因是两套数据源没统一。

### 三个演示数据一致性问题一次修完（投料区恒0 / 状态全烹饪中 / 状态与盆数打架）
用户确认修。方案核心：给「生产进度」面板建一套**自己的烹饪时钟**，不再借用流程图的动画相位。

1. **新增 `cookPhase(dish)`**：`(flowNow - flowStartedAt)/LINE_CYCLE_MS + idx/DISHES.length) % 1`——每道菜按 DISHES 索引错开 0.1 的固定偏移，确定性、不手工挑、随产线时钟（80ms tick）实时推进。
2. **新增 `cookState(dish)`**（面板专用状态）：`done===0 → 未开始`、`done===total → 取餐完成`、中间态看相位（`<0.15 → 称重中`，否则 `烹饪中`）。起止两档由盆数决定 → **状态与盆数永远同源**，「蒸蛋羹未开始但 2/3 盆」的打架消失。
3. **新增烹饪信息常量** `COOK_DURATION_SEC`（粥25min/蒸蛋12min/青菜6min/炒菜8min/番茄6min/土豆烧牛肉40min…）、`COOK_TARGET_TEMP`（炒菜~190℃/烤箱160℃/蒸粥~100℃）。「烹饪中」的行在状态胶囊旁显示 `已烹饪 X / 总时长 · 温度℃`，由 cookPhase 插值（温度 = 60 + phase×(目标-60)）。
4. **投料区 KPI 换口径**：`feedingRoutes`（动线在入口通道）→ `segmentDishes.filter(d => cookState(d)==='称重中').length`。晚餐从恒 0 变成 {0,1,2} 实时变化；`feedingRoutes` 成死代码已删（`isTrayWaiting` 仍被流程图托盘高亮用，保留）。
5. **列宽重排**（状态列要装胶囊+两行小字）：`150|210|150|120|104|130`（总和仍 864 + gap 70 = 934）。状态列 92→210，进度条 212→130 仍够用。

**关键取舍（记下来，避免以后被问倒）**：`workOrderStatus`（动画相位驱动、跟流程图托盘绑定）**没动**，出餐统计页筛选器、设备管理页任务表仍用它。两套口径分工：生产进度面板 = 本餐实时烹饪快照（cookState）；其余 = 全局工单状态（workOrderStatus）。

**踩坑**：`cookState` 最初定义在 `dishState` 之后，而 `segmentFeedingTrays`（在前面）引用它 —— const 暂时性死区直接 ReferenceError。**必须把被依赖的函数定义在引用点之前**。

**验证**（500ms × 30 采样 × 3 餐段，脚本 /tmp/finalchk.py）：投料区 早{0,1}/午{0,1,2}/晚{0,1,2}；状态组合数 2/4/6（晚餐不再单一）；时间温度 2 秒内实测变化；console 0 错误、无裁剪。

**已知观感特性（用户未反馈，先记录）**：已烹饪时间随 14s 演示循环走完 0→总时长再回 0（与托盘动画同节奏），评审时若被问「时间怎么倒回去」，答「演示是循环播放，一轮=一道菜从开火到出锅」。
